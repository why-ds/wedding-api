# 웨딩 검색·비교 플랫폼 개발 착수안

작성일: 2026-09-07. 첨부 설계서 및 SQL과 현재 `wedding-pai` 프로젝트를 검토한 결과다. 기존 설계를 대체하는 문서가 아니라, 구현 범위와 보완할 계약을 정리한 후속안이다. 아래 변경은 제안이며 실행한 DB 마이그레이션이 아니다.

## 1. 결론

기존 설계를 기반으로 진행한다. 핵심 가치는 **같은 날짜·인원·구성 조건에서 업체별 예상 총액과 포함 항목을 비교하는 것**이다. 업체 소개 페이지 수보다 가격 데이터의 완전성과 비교 조건의 일치가 우선이다.

업종 7개와 공통 도메인은 유지하되, 첫 구현은 예식장으로 전체 흐름을 완성한다. 이어 스튜디오 단품으로 다른 업종에도 모델이 맞는지 검증하고 드레스·메이크업 및 확정 패키지, 예물·한복·정장을 확장한다. 이는 출시 카테고리의 영구적인 축소가 아니라 구현 순서다.

61개 테이블 전체를 한 번에 Entity와 CRUD로 만드는 작업은 첫 완료 목표로 삼지 않는다. 검색·가격·게시 검증에 실제로 필요한 기능부터 구현한다.

## 2. 현재 확인한 상태

| 항목 | 확인 결과 |
|---|---|
| 첨부 설계 | 업무 규칙, 7업종 사양, 가격 계산, 검색, 권한, 단계별 확장 포함 |
| 첨부 SQL | `CREATE TABLE` 61개, 9개 스키마, FK·CHECK·EXCLUDE 및 인덱스 포함 |
| 기존 서버 | Spring Boot 4.1.1, Java toolchain 21, Gradle 9.7.1 설정 |

| 애플리케이션 | 부트스트랩 클래스와 기본 테스트 존재. 업무 코드 없음 |
| 설정 | application.yaml에 애플리케이션 이름만 존재 |
| 프런트엔드 | 확인한 프로젝트 파일에 React 프로젝트 없음 |

| 로컬 도구 | PATH에서 java는 확인. docker와 psql은 발견되지 않음. 별도 설치·원격 DB 부재를 뜻하지는 않음 |

기존 자료의 시장 조사·가격·법률 설명은 이번에 모두 재검증한 결과가 아니다. 이번 검토는 제공된 자료와 코드 사이의 구현 준비도를 중심으로 진행했다.

## 3. 유지할 구조

```text
organization: 사업 주체
  └─ branch: 영업 지점
      └─ listing: 지점의 업종별 소개
          └─ product: 제공 상품
              └─ product_version: 특정 시점 사양
                  └─ 업종별 spec

offer: 판매처·채널별 판매 제안
  └─ offer_revision: 구성·가격·약관 버전
      ├─ offer_component → product_version
      └─ charge → charge_rule / charge_relation

사용자 조건 + 판매 제안 버전 → estimate + estimate_line
같은 공통 요구사항의 estimate 묶음 → comparison
```

한 업체가 여러 업종을 운영할 수 있으므로 예식장업체·스튜디오업체별로 계정과 사업자 테이블을 복제하지 않는다. 업종의 차이는 listing/category와 상품의 전용 spec으로 표현한다.

상품 제공자와 판매자는 분리한다. 패키지 기본가에 이미 포함된 단품 기본가를 다시 합산하지 않는다. 업체별 조건 총액과 광고 시작가도 별개의 값으로 유지한다.

Spring 애플리케이션 하나와 PostgreSQL 하나를 사용한다. DB 스키마의 개수와 배포 서비스의 개수는 무관하다.

## 4. 구현 전에 보완할 데이터 계약

### 4.1 반환형 보증금의 미확인·범위 상태

현재 `pricing.estimate.refundable_security`는 NOT NULL 단일 금액이며 기본값은 0이다. 이를 그대로 사용하면 보증금이 없다는 사실과 보증금 금액을 모른다는 상태를 구분하기 어렵다.

변경 제안:

- `security_state`: NONE / FIXED / RANGE / UNKNOWN.
- `security_min`, `security_max`: NONE은 둘 다 0, FIXED는 동일한 비음수, RANGE는 0 ≤ min < max, UNKNOWN은 둘 다 NULL.
- 기존 소비 비용의 `state`와 별도로 관리한다. 소비 비용은 확정 범위여도 보증금은 미확인일 수 있다.
- 화면에 소비 비용과 추가로 필요한 보증금을 각각 표시한다. 계약 선납금은 비용에 재합산하지 않는다.

기존 열을 대체할지 호환 열로 잠시 둘지는 최초 DB 적용 여부를 확인한 후 결정한다. 이미 적용한 V1은 수정하지 않고 후속 마이그레이션으로 변경한다.

### 4.2 할인과 범위 금액 계산

기존 설계의 PERCENT와 범위 가격은 유지하되, 엔진 구현 계약을 추가한다.

- 독립적인 비용 범위 A=[a,b], 할인 범위 D=[c,d]의 차는 [a-d,b-c]다. 하한끼리, 상한끼리 빼지 않는다.
- 비용 100~120만원에서 고정 10% 할인은 90~108만원이다. 할인액과 비용이 연동되므로 독립 범위처럼 계산하지 않는다.
- 할인은 지정된 기준 항목을 넘지 못하도록 게시 정책을 검증한다. 검증된 별도 정책 없이 음수 총액을 허용하거나 0으로 조용히 보정하지 않는다.
- 세금 적용 순서, 할인 기준의 세전·세후 여부, 항목별 원 단위 반올림은 버전이 있는 pricing policy로 검증한다.
- `estimate_line`의 할인은 음수 금액으로 기록하고, 보증금은 소비 비용 합계에서 제외한다. 계산 스냅샷에 effect·선택한 rule·수량 근거·정책 버전을 명시한다.
- `known_subtotal`은 확인된 소비 비용의 순소계로 정의한다. 정상 저장 결과는 비음수이고, 미확인 비용이 있는 경우 전체 총액이라고 표현하지 않는다.

### 4.3 DB가 아직 보장하지 않는 행 간 규칙

다음은 기존 설계서에도 서비스 검증 대상으로 적혀 있다. SQL에 FK가 있다는 이유로 구현을 생략하면 안 된다.

| 대상 | 추가 구현 | 책임 서비스 |
|---|---|---|
| comparison_item | 견적의 공통 조건 해시·scope 일치, 다른 프로젝트의 비공개 견적 차단, 익명 견적 저장 시 소유 연결 | ComparisonService |
| review_rating | 평가 기준의 업종과 후기 대상 listing 업종 일치 | ReviewService |
| inquiry | 동의 사용자·수신 업체·목적·항목·철회 여부와 프로젝트 편집 권한 검증 | InquiryService |
| product_version/spec | 공개 시 전용 spec 존재 및 사용 가능한 사양 검증 | ProductPublicationService |
| offer_revision 하위 구성 | 승인된 제공 상품, 공급 관계, 가격 규칙 충돌·순환·중복 청구 검증 | OfferPublicationService |
| 공개 버전·견적 | 과거 구성과 계산 근거의 불변성, 새 버전 생성 | 전용 변경 서비스 및 DB 권한/트리거 |

게시와 하위 데이터 수정이 같은 부모 행 잠금을 사용해야 한다. 게시 API만 잠그면 다른 경로에서 단가를 변경할 수 있다. 사용자·업체 공개 API에는 Entity를 그대로 노출하지 않는다.

PostgreSQL CHECK는 NULL 평가를 허용하며, 다른 행의 일관성을 보장하는 용도로 사용할 수 없다. 단순 금액·NULL 조합은 CHECK/NOT NULL, 참조 관계는 FK, 게시·권한 규칙은 트랜잭션 내부 검증으로 분담한다. [PostgreSQL 제약 공식 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)

### 4.4 직원의 지점 권한

현재 `organization_member`는 PK가 `(organization_id,user_id)`이고 `branch_id`가 하나다. 직원 한 명을 일부 지점 여러 곳에 배정할 수 없다.

업체 포털 구현 때 `organization_member`에 조직 소속과 조직 역할을 두고, `organization_member_branch(organization_id,user_id,branch_id,role,status)`로 지점 배정을 분리한다. 소속·지점의 조직 일치는 복합 FK로 보장한다. 모든 지점을 허용하는 조직 역할과 특정 지점 역할의 우선순위도 명시한다.

첫 내부 데이터 검증 화면에는 필요하지 않지만, 지점별 권한이 있는 업체 포털 공개 전에는 결정해야 한다. 초기 직원 권한을 조직 전체로 제공하기로 한다면 범위를 명시하고 이후 확장한다.

### 4.5 검색 결과의 단위와 가격 정렬

단순 업체 탐색은 listing 단위, 총액 비교 검색은 offer_revision 단위로 고정한다. 하나의 지점에 여러 홀·판매처가 있으므로 응답에 listingId, hallId(해당 시), offerId, offerRevisionId, seller를 함께 제공한다.

- 동일 제공업체의 판매 제안은 그룹으로 표시하고 업체 수와 판매 제안 수를 구분한다.
- 총액 오름차순 제안: 계산 완료 결과의 total_max, total_min, offerRevisionId 순. 범위 상한을 기준으로 한다는 설명을 화면에 표시한다.
- PARTIAL/UNAVAILABLE은 별도 그룹으로 표시하고 소계를 총액 정렬에 넣지 않는다.
- 가격 필터·정렬 이후 페이지를 나눈다. 페이지를 먼저 선택해 계산하지 않는다.
- 후속 페이지에는 검색 조건 해시와 고정된 결과 기준을 사용한다. 요청 도중 가격이 바뀌면 동일 결과 스냅샷을 유지하거나 명시적으로 다시 검색한다.

### 4.6 견적 캐시와 데이터 변경

context_hash만으로 유효성을 결정하지 않는다. 게시 가격의 내용은 버전으로 고정하되 업체 중단·공급 관계 철회·자료 재확인 기한·공휴일 데이터 변경도 고려한다.

- 견적 expires_at은 계산에 사용한 유효기간 종료와 운영상 캐시 만료 중 가장 이른 시점 이내로 정한다.
- 공휴일 및 외부 정책처럼 가격표 밖의 입력도 스냅샷에 근거·버전을 기록한다.
- 관련 근거가 정정되면 캐시를 무효화하고 새 estimate를 만든다. 과거 견적은 보존한다.
- 검색 projection이 갱신되기 전이라도 공개 읽기에서 업체·상품·제안의 현재 공개 가능 상태를 확인한다.

## 5. 첫 구현 범위와 구조

기존 `wedding-pai`를 서버로 유지하고, 프런트는 작업공간의 형제 디렉터리 `wedding-web`으로 추가하는 안이다. 프런트는 기존 문서의 React + TypeScript + Next.js 제안을 이어가되 구체적인 버전은 생성 시 고정한다.

```text
D:/dev/wedding/
  wedding-pai/
    docs/
    src/main/java/com/wedding/
      identity/
      partner/
      catalog/
      pricing/
      planning/
      scheduling/
      engagement/
      search/
      operations/
    src/main/resources/db/migration/
  wedding-web/
```

패키지는 구현하는 도메인부터 만든다. pricing은 프레임워크·DB에 의존하지 않는 계산 코어와 조회·저장하는 application 계층으로 나눈다. PostgreSQL range 및 복합 조회는 명시적 SQL로 다루고, JPA 연관 그래프로 모든 도메인을 묶지 않는다. 실제 드라이버·ORM에서 range/JSON 매핑을 검증한다.

공개 웹과 Spring API는 같은 사이트의 `/api` 경로로 제공하는 구성을 기본안으로 한다. 가격 계산과 업무 권한은 Spring에 둔다. 프런트는 받은 금액을 표시하고 필터·선택 상태를 관리한다.

## 6. 개발 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 0. DB 기반 | Java 21 실행환경, 개발 전용 PostgreSQL, Flyway, 환경변수 설정, 실패 시 롤백 확인 | 빈 DB 마이그레이션 성공, 재실행 시 중복 적용 없음, 관련 FK/CHECK/EXCLUDE 검증 |
| 1. 데이터 입력 | 출처·업체·지점·예식장 listing·홀·상품 버전·판매 제안·비용 입력과 게시 검증 | 가상 3개 홀의 서로 다른 조건을 저장하고 조회 가능 |
| 2. 가격 엔진 | 성인 보증인원, 대관·장식·식대, 세금, 고정/범위/미확인, 선택 비용 | 기존 설계 A홀 2,700만원/B홀 2,650만원 재현, 단위 테스트 통과 |
| 3. 첫 사용자 화면 | 지역·날짜·인원 검색, 상세, 총액 내역, 2~5개 비교 | 브라우저에서 같은 조건의 총액과 포함 항목·미확인 비용 확인 |
| 4. 업종 확장 | 스튜디오 단품 → 드레스·메이크업 → 확정 패키지 → 예물·한복·정장 | 업종별 비교 요구를 충족하며 포함 가격 이중 계산 없음 |
| 5. 사용자·업체 운영 | 로그인·프로젝트·찜·문의·동의·답변·증빙 후기·업체 제출·운영 승인 | 타 프로젝트/타 업체 접근 거부, 동의·게시·중복·정정 시나리오 통과 |

단계 1의 내부 입력은 통제된 개발용 seed/도구로 시작할 수 있다. 쓰기 API나 운영 UI를 외부에 공개하기 전에는 인증·권한을 먼저 적용한다. 단계 3의 비교는 비회원 임시 비교이며 계정에 영구 저장하는 기능은 단계 5다.

첫 데이터는 **가상 데이터**를 명확히 표시한다. 실제 시세·리뷰처럼 공개하지 않는다. 개발과 함께 승인된 실제 업체 가격표를 대입해 모델의 빈틈을 검증한다. 한 지역에서 소수 업체로 검증하는 것은 초기 운영 제안이며 전국 서비스 범위 변경을 뜻하지 않는다.

## 7. 최초 API 계약

| API | 첫 구현의 책임 |
|---|---|
| GET /api/v1/categories | 업종과 지원 필터 |
| GET /api/v1/listings | 지역·업종·이름 기반 공개 업체 탐색 |
| GET /api/v1/listings/{id} | 업체·홀·제공 상품·판매 제안 상세 |
| GET /api/v1/offers/{id} | 현재 적용할 revision 및 구성·가격 조건 |
| POST /api/v1/estimates | 지정 조건의 예상 금액·상태·항목·미확인 이유 |
| POST /api/v1/searches | 동일 조건으로 전체 후보 계산 후 가격 필터·정렬 |

기존 문서의 요청/응답 형식을 기본으로 쓰되 `knownSubtotal`, 가격 확인일, 만료일, 공통 비교 조건 해시, 보증금 상태·범위를 응답 계약에 포함한다. 금액은 십진 문자열, 알 수 없는 금액은 null이다. 일정 확인 상태는 가격 상태와 별도다.

## 8. 마이그레이션 적용 원칙

첨부 SQL은 설계용 원본으로 보존한다. 실제 Flyway 경로에 넣기 전에 보완 사항을 반영하고 전용 PostgreSQL에서 실행한다. 이미 적용된 DB가 있다면 원본 V1을 변경하지 않고 V2 이후로 수정한다.

Flyway가 마이그레이션의 트랜잭션을 관리하므로, 배포용 파일에서는 원본의 바깥 `BEGIN/COMMIT`을 제거해 트랜잭션 소유를 일원화하는 안을 채택한다. 수동 psql 실행용 원본의 트랜잭션은 그대로 보존한다. [Flyway 트랜잭션 공식 문서](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/migration-transaction-handling)

pg_trgm/btree_gist 생성 권한, DB 마이그레이션 소유자와 앱 실행 권한, 스키마 명시, ORM의 스키마 자동 변경 금지를 검증한다. 개발용 seed는 운영 마이그레이션과 구분한다.

시간 구간은 `[시작,종료)` 입력 계약과 경계 테스트를 둔다. timestamp range의 경계는 명시적으로 검증한다. [PostgreSQL range 공식 문서](https://www.postgresql.org/docs/18/rangetypes.html)

## 9. 우선 검증할 수용 시나리오

1. 성인 250명·보증 300명에서 300명 식비를 계산한다.
2. VAT 포함 가격에 세금을 다시 더하지 않는다.
3. 필수 비용 미확인 결과는 PARTIAL이고 가격순 최저가로 올라가지 않는다.
4. 보증금 UNKNOWN을 0원으로 표시하지 않는다.
5. 패키지 포함 단품과 기본가를 중복 청구하지 않는다.
6. 연동된 할인 범위의 계산을 실제 구성과 일치시킨다.
7. 같은 우선순위의 단가 조건이 겹치면 게시를 거부한다.
8. 12시 종료 구간과 12시 시작 구간의 경계가 중복 적용되지 않는다.
9. 가격 갱신 뒤 과거 견적은 유지되고 신규 계산만 새 가격을 쓴다.
10. 뒤쪽 후보가 더 저렴한 데이터에서도 전체 총액 정렬이 맞는다.
11. 공개 중단·근거 정정이 캐시보다 먼저 사용자 표시를 제어한다.
12. 게시와 하위 단가 수정의 동시 요청에서 미검증 가격이 노출되지 않는다.

수식은 단위 테스트, 제약·잠금·마이그레이션은 실제 PostgreSQL 통합 테스트, 검색·비교는 API 및 브라우저 흐름으로 검증한다. 이 문서 작성 단계에서는 해당 테스트를 실행하지 않았다.

## 10. 후속 결정 사항

개발 기본값은 국내 정보 검색·비교와 견적 문의 연결이다. 첫 검증 지역과 실가격 공급처, 고객 로그인 제공자, 업체 직접 등록 시점, 지도 제공자, 수익 모델은 후속 결정으로 남긴다. 지도·결제·실시간 예약 연동 없이도 1~3단계는 구체화할 수 있다.
